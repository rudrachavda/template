# Design System & Code Guidelines

Ported from `bento` (personal portfolio) — the design language this template
is built on. This file, not `AGENTS.md`, is where the design rules live:
`AGENTS.md` is regenerated by `next dev` itself (see the marked block inside
it) and shouldn't be hand-edited for this.

**Standing principle**: this is a template for *any* web app, not a
portfolio. Visual language (colors, type, shape, motion) ports over as-is —
that's the point — but a component's *behavior* shouldn't assume portfolio
content (an always-external link, a fixed "back to my projects" target, a
hardcoded page title). When porting or adding something to `components/`,
keep the site-specific parts (an href, a label, what icon) as props supplied
by the call site, and keep the shared component itself general. See §6 for
the concrete example (`Button`).

## 1. Color System

Three-tier surface hierarchy, each tier a light/dark pair, defined as CSS vars
in `app/globals.css` `@theme`:

| Tier | Light | Dark | Used for |
|---|---|---|---|
| Background | `#fefefe` | `#121212` | `<body>` |
| Primary surface | `#fafafa` | `#1d1d1d` | Card fills |
| Secondary surface | `#f0f0f0` (or `#fff`) | `#171717` | Nested/secondary panels |

Hairline border, on every card/bordered surface, `border-[0.5px] border-solid`:
```
border-[rgba(225,228,232,0.8)] dark:border-[rgba(29,29,29,0.8)]
```
If nesting a border inside another border, a plain `border` (no explicit
width) avoids doubled hairlines.

Persistent chrome (a header/nav bar, a footer) should use the **secondary
surface** tint (`bg-[#f0f0f0] dark:bg-[#171717]`), not the plain background —
otherwise it reads as flush with the page content instead of a distinct band
of UI. Reserve the plain background for the actual content area.

Text colors (`#1d1d1d`/`#f0f0f0` pair — **not** `zinc-100`, that's a
button-only idiom, see §4):
- Primary text: `#1d1d1d` light / `#f0f0f0` dark, always paired with `dark:antialiased`.
- Secondary text: `#646464` (subtitle/label) or `#a1a1a1` (secondary/muted — dates, numbers).
- Selection highlight: `background: #ededed; color: #1d1d1d`.

Accent palette (gradients, status colors — not surface colors):
```
#9659b9 #ee98b7 #1a2b3b #0069cc #50aef6 #abcdef #169b40 #0a461d #fcd609 #fc9601 #b64400 #fc3e2f
```
`#1a2b3b` doubles as the default `Shadow` component tint. `#169b40` is the
success green. `#0088ff` is the inline-link blue.

## 2. Typography

Self-hosted **Inter Variable** (`public/fonts/Inter/InterVariable.ttf` via
`next/font/local`, not `next/font/google`), optical size locked to text mode
(`font-variation-settings: "opsz" 14`), with a curated feature-setting list.
`font-mono` is the system UI-monospace stack. `SpaceGrotesk`/`HaloGrotesk` are
registered as `@font-face`s but not wired into any component yet — available,
currently dormant.

The whole system runs on **one size**: `text-sm`, almost always `font-medium`,
`tracking-normal`. Variation comes from color and leading, not size — see the
`Text` component (`components/typography/text-styles.tsx`):

| Role | Classes |
|---|---|
| Title | `text-sm leading-snug font-medium tracking-normal text-pretty text-[#1d1d1d] dark:text-[#f0f0f0] dark:antialiased` |
| Subtitle | `text-sm leading-snug font-medium tracking-normal text-pretty text-[#646464]` |
| Paragraph | `text-sm leading-relaxed font-medium tracking-normal text-[#1d1d1d] md:text-pretty dark:text-[#f0f0f0] dark:antialiased` |
| Secondary | `text-sm leading-relaxed font-medium tracking-normal text-[#a1a1a1] md:text-pretty` |
| Label | `text-sm leading-relaxed font-medium tracking-wide text-[#646464] uppercase md:text-pretty` |

`components/typography/header.tsx` is the one deliberate exception
(`font-[590] leading-5.25`) — reserved for section headers, don't reuse the
weight elsewhere.

Numbers/data columns: `font-mono` with `tabular-nums` for alignment.

**tailwind-merge gotcha**: `cn()`/`twMerge()` treats a `text-*` (font-size)
utility as conflicting with `leading-*` — a `text-*` that comes *after* a
`leading-*` in the merged string silently strips it. Always write
`text-sm leading-relaxed`, never the reverse order.

## 3. Layout & Spacing

Reading column width: `max-w-173` (~692px), via `Section`
(`components/layout/section.tsx`, `variant='restricted'` is the default —
`mx-auto w-full max-w-173 px-6 flex`). `variant='full'` drops the constraint
for hero/screenshot sections that should bleed edge to edge.

Chronological/data lists use a fixed-label + flexible-content grid:
`grid-cols-[3.75rem_1fr] md:grid-cols-[6.75rem_1fr]`.

**4px grid**: every spacing/sizing value — padding, margin, gap, width/height,
inset — should land on a multiple of 4px (Tailwind's `1`–`96` scale already
*is* this grid: `p-1`=4px, `p-2`=8px, `p-4`=16px, `size-9`=36px, etc., so
sticking to whole Tailwind steps gets this for free). The one allowed
exception is **6px** (Tailwind's `1.5` step — `py-1.5`, `gap-1.5`), used for
tight rhythm inside compact controls. Half-steps other than that (`0.5`=2px,
`2.5`=10px, `3.5`=14px, `4.5`=18px) and arbitrary pixel values (`gap-[10px]`,
`mr-[3px]`) don't comply — round to the nearest 4px step instead (an
in-between icon size like 18px becomes `size-4`(16px) or `size-5`(20px), not
`size-4.5`).

## 4. Shape Language — Squircle

`components/ui/squircle/` renders a true superellipse via SVG path, not CSS
`border-radius`. Two fixed idioms — don't invent a third without reason:
- **Card/button squircle**: `radius={12} exponent={5} smoothing={1}`.
- **Pill/circle**: `radius={999} exponent={2} smoothing={1}` (true circular math).

`smoothing` is always `1`. For proportional corners at arbitrary sizes:
`radius = round(height * 0.42)` (`squircle/tokens.ts`, `radiusFor()`) — this
is what `Button` actually uses per size (`sm`/`md`/`lg` → 12/15/18px), not a
flat `radius={12}` regardless of height. `pill`/`icon` sizes still force
`radius={999}` (true circular math, `exponent={2}`).

**Rule**: never pair a `Squircle` with a Tailwind `shadow-*`/`box-shadow` class
— the shadow cuts inside the squircle's real edge. Use `filter: drop-shadow(...)`
instead, since it traces the rendered alpha silhouette. See §5.

## 5. Shadows

Two separate, non-interchangeable systems — pick by what's casting the shadow:

- **`Shadow` component** (`components/ui/shadow.tsx`) — for plain
  `border-radius` surfaces. Five-layer stack, scaled by `elevation`/
  `intensity`, tinted by `hexColor` (default `#1a2b3b`), applied as an inline
  `boxShadow` (so a `dark:shadow-*` Tailwind class won't touch it — pass a
  `darkHexColor` prop if it needs to differ by theme). Its light-mode inner
  highlight ring is written but commented out in the source — dead code, not
  a missing feature to restore casually.
- **`drop-shadow(...)`** — required for anything shaped by `Squircle`, since
  `box-shadow` is clipped to a `border-radius` arc, not the real superellipse
  edge. The card idiom disables it entirely in dark mode, not just dims it:
  ```
  [filter:drop-shadow(0_1px_1px_rgba(28,29,33,0.13))_drop-shadow(0_6px_7px_rgba(28,29,33,0.07))]
  dark:[filter:none]
  ```

## 6. Buttons & Interactive Components (`components/ui/buttons.tsx`)

`Button` is a **general-purpose** primitive — any button anywhere, not a
component fine-tuned for one site's social-link row. Every clickable shape
still paints its own surface as a `Squircle` with `fill="currentColor"` (the
wrapper's text-color class *is* its background, label/icon sit in a
`relative z-10` layer above it), but the API is generic:

- **`variant`**:
  - `solid` — a real, always-visible inverted surface, the primary-action
    look: `text-[#1d1d1d] hover:text-zinc-700 dark:text-[#f0f0f0]
    dark:hover:text-zinc-300`, label always the opposite tone
    (`text-[#f0f0f0] dark:text-[#1d1d1d]`) and constant, not hover-flipped.
    Deliberately **not** the old `zinc-100`/`zinc-950` icon-button idiom —
    `zinc-100` sits almost indistinguishably close to the `#fefefe` page
    background at rest, reading as an invisible button until hovered. That's
    fine for a quiet icon-only control (see `ICON_LABEL` below), wrong for
    the one variant meant to be the obvious primary action.
  - `outline` — transparent + a real `Squircle` `stroke` using the
    `--border-hairline` CSS var, so it flips with `.dark` without a
    `useTheme()` round-trip.
  - `ghost` — transparent, no border, tints on hover only.
- **`size`**: `sm`/`md`/`lg` map to `CONTROL_H_SM`/`CONTROL_H`/`CONTROL_H_LG`
  (28/36/44px, `squircle/tokens.ts`) with the corner radius derived via
  `radiusFor(height)` so every size stays proportionally consistent. `icon`
  is a fixed 36px square — same proportional radius as any other size, not
  automatically round.
- **`pill`**: forces `radius={999}` (a true circle/stadium, `exponent={2}`)
  on *any* size, `icon` included. Shape is orthogonal to size — an icon
  button defaults to the same soft-rounded corner as a text button; ask for
  `pill` explicitly when a circular icon button is what you actually want
  (e.g. an avatar-style trigger), don't assume every icon button is round.
- **`href` auto-detects internal vs. external**: an internal path renders a
  Next `Link` (client-side nav, same tab); anything matching
  `isExternalHref()` (`http(s)://`, `mailto:`, `tel:`, protocol-relative
  `//`) renders a plain `<a target="_blank" rel="noopener noreferrer">`. No
  `href` at all renders a native `<button>`. One component, three render
  modes — don't reach for a parallel "internal-only" button like the old
  `PillLink` again; fix/extend `Button` instead. `Button` doesn't auto-append
  an outbound-arrow icon for external links either — not every button that
  happens to have an external `href` wants one signaled; pass one explicitly
  via `trailingIcon` when it's actually wanted.
- Icon-only buttons (`size="icon"`) get their own coloring regardless of
  variant — muted at rest, full contrast on hover:
  `text-[#a1a1a1] group-hover:text-[#1d1d1d] dark:text-[#646464] dark:group-hover:text-[#f0f0f0]`.
- Press feedback: `active:scale-[0.97] active:brightness-[1.04]
  transition-[color,scale,filter] duration-200` (not `transition-[transform,...]`
  — see the v4 gotcha in §7, `scale-*` is the same story as `-translate-y-*`).
  Plain CSS, not `whileHover`/`whileTap` — `Button` has no framer-motion
  dependency of its own, so it renders identically whether it's a `<button>`,
  `<a>`, or `Link`.
- `disabled` sets `pointer-events-none opacity-50` and, for link-mode,
  `aria-disabled`/`tabIndex={-1}` (an `<a>`/`Link` has no native `disabled`).
  Every render mode gets a visible `focus-visible:ring-2` — keyboard-focus
  states aren't optional.

**No `Magnetic` by default** — it's a special-occasion detail, not something
`Button` bakes in for every instance. If one specific button truly wants a
magnetic pull (a hero CTA, a social-link row), wrap that call site directly —
`<Magnetic><Button ...>` — rather than adding a prop that reintroduces it
everywhere. Composition over configuration here. `actionArea="global"`
(tracks the pointer anywhere on the page, not just on hover) is the version
to be most wary of — on anything clicked often, it reads as fidgety, not
delightful.

`Back`/`Copy` are thin, generic wrappers on top of `Button`
(`variant="ghost" size="icon"`), not one-off components: `Back` takes an
optional `href` and falls back to `router.back()` when omitted (a "back"
button doesn't always have one fixed destination), `Copy` copies the current
URL and is a reasonable "copy/share link" affordance for any app.

**A recurring question for anything new in `components/`**: is this
behavior specific to one site's content (a portfolio's "back to my
projects list", a fixed external social link), or is it a shape any app
would reuse? Keep the former out of shared components — put it in the
page/route that actually needs it — and design the latter so the *site*
supplies the specifics (an href, a label, an icon) while the component stays
opinion-free about what they are.

## 7. Motion (`motion/react`, package name `motion` — not the legacy
`framer-motion` alias)

Two named variants (`components/motion/variants.ts`), reused everywhere
lists/sections animate in — always name them `container`/`item`, never inline
one-offs:
```ts
container: { visible: { transition: { staggerChildren: 0.1 } } }
item: {
  hidden:  { opacity: 0, y: 12, filter: 'blur(12px)' },
  visible: {
    opacity: 1, y: 0, filter: 'blur(0px)',
    transition: { type: 'spring', damping: 25, stiffness: 200 },
    transitionEnd: { filter: 'none' },
  },
}
```

Interaction timing, by what's moving:
- Color/opacity hover: `duration-200 ease-out`.
- Larger movement (lift/position): `duration-300`–`400 ease-in-out`.
- Press feedback: `duration-150`.

**Tailwind v4 gotcha**: `-translate-y-*` and `scale-*` utilities set the
individual CSS `translate`/`scale` properties, not the combined `transform`.
A `transition-[transform,filter]` list silently misses both — list
`translate`/`scale` explicitly (whichever the hover/active state actually
uses) instead of reaching for `transform`.

## 8. Iconography

No icon registry or icon font. Two sources only:
- `lucide-react` — generic utility glyphs only (e.g. the theme switcher's
  `Monitor`/`Moon`/`Sun`, at `h-4 w-4`).
- Hand-authored inline SVGs everywhere else, `fill="currentColor"`, sized and
  colored with Tailwind classes directly on the `<svg>` tag.

## 9. Code Conventions

**Tailwind class ordering** — settled rule, not a suggestion:
1. Background (`bg-white`, `dark:bg-zinc-800`, `hover:bg-zinc-950`)
2. Border / shape (`border`, `rounded-md`, `ring-2`)
3. Typography (`text-sm`, `font-medium`, `tracking-normal`, `leading-snug`)
4. Text color (`text-black`, `dark:text-zinc-100`, `hover:text-zinc-50`)
5. Position (`absolute`, `relative`, `z-10`, `top-0`)
6. Flex/grid/size (`flex`, `items-center`, `w-full`, `gap-2`, `shrink-0`)
7. Everything else (`px-4`, `transition-all`, `duration-300`, `cursor-pointer`)

**Simple elements stay on one line** — a JSX element with no complex nested
logic (`<p className="...">{description}</p>`) shouldn't be broken across
three lines just because it has a long class string.
